## Top 3 most concerning

1. **F-001 (High)** — `vegastack preview` runs user-supplied `--command` through `spawn(..., { shell: true })`, enabling shell injection from any value passed on the CLI or detected from `package.json` scripts.
2. **F-002 (High)** — Archive extraction in managed-tool / cloudflared / ripgrep / gitleaks installers shells out to `tar -xzf` / `unzip` with **no zip-slip / symlink / device-file pre-validation**. 3. **F-003 (High-ish/Medium)** — The `tests/fixtures/safe-tar/traversal.tar.gz` fixture exists but `rg -n "fixtures/safe-tar|traversal\.tar"` returns **no hits in tests or src** — the hardening test the fixture was added for is not wired up. ## Findings

### F-001 — Shell injection via `vegastack preview --command` [High]
- File: `src/commands/preview.ts:85, 167-184, 186-190`
- `spawnShell(command)` calls `spawn(command, { shell: true, ... })`. The command is sourced from `opts.command` (CLI flag), or constructed from detected package manager + script name in `detectDevCommand`. While the manager strings are constants, the user-passed `--command` is unvalidated and runs under `/bin/sh -c`, so e.g. `--command "npm run dev; rm -rf ~"` would execute. Acceptable for an interactive dev command, but should be documented as untrusted-input-equivalent and the CLI should refuse if invoked from non-interactive contexts (CI, scripts) without an explicit opt-in.
- Recommendation: drop `shell: true` and parse via `string-argv`/equivalent, or gate behind a confirm prompt + env opt-out (`VEGASTACK_PREVIEW_ALLOW_SHELL`).

### F-002 — Archive extraction lacks pre-validation in 4 installers [High]
- Files:
  - `src/lib/managed-tool-installer.ts:179, 183-191, 194` (`tar -xzf`, PowerShell `Expand-Archive`, `unzip`)
  - `src/lib/cloudflared.ts:157`
  - `src/lib/ripgrep.ts:155, 159, 170`
  - `src/lib/gitleaks.ts:156, 160, 173`
- Mitigations in place: archive bytes are SHA-256 verified before extract (good — assumes publisher upstream not malicious). However a single compromised upstream release (gitleaks/trivy/cloudflared/ripgrep) would let a tarball with `../` paths, symlinks pointing to `/etc/...`, or device files write outside `targetDir` because no pre-check is done.
- Compare with the **good** path: `src/lib/registry.ts:447-466` lists with `tar -tzf` and runs `assertSafeRelativePath` per entry. Apply the same pattern to the four installers and forbid `--symlinks`/device entries (`tar` with `--no-same-permissions --no-same-owner` and post-list scan; or use a JS tar lib like `tar` package with `strict: true` + filter).
- Note: relying on a SHA-256 of the upstream archive is insufficient if the upstream signing key is ever compromised — pre-extract validation is the second line of defense.

### F-003 — Traversal fixture not exercised by tests [High]
- File: `tests/fixtures/safe-tar/traversal.tar.gz` exists, but `rg -n "fixtures/safe-tar|traversal\.tar" tests src` returns nothing. The fixture is dead.
- Recommendation: add a vitest case that calls each extractor with the fixture and asserts `ArtifactCorrupt`; track via this finding.

### F-004 — Update channel runs `npm view` without `--no-update-check` flag [Medium]
- File: `src/lib/update-check.ts:64`, `src/cli.ts`
- `printUpdateNagIfStale` is **read-only / cache-only / non-blocking** (good) and only refreshes the cache during `vegastack doctor` / `vegastack update`. There is **no auto-execute** of installs (good). However, the env opt-out is `VEGASTACK_NO_UPDATE_NAG` only — there is no `--no-update-check` CLI flag despite the task brief implying one should exist. CI users have to know the env var.
- Recommendation: add `--no-update-check` global flag, plus respect `CI=true` heuristically.

### F-005 — postinstall ends with non-zero swallow on the spawnSync timeout [Medium]
- File: `npm/install.js:48-53`
- The script does NOT end with `|| true` (the brief was outdated — that line is no longer present). However, all errors are written to stderr only and exit code is always 0 (the script never `process.exit(1)`s). That's actually correct for postinstall (don't break `npm i`), but the script does **not** honor `npm_config_ignore_scripts` (npm enforces that itself, not the script). It does honor `VEGASTACK_SKIP_POSTINSTALL=1` and `VEGASTACK_SKIP_SKILL_INSTALL=1`. Network calls: none in postinstall (good). File writes: only to user agent dirs via the spawned `vegastack skills reconcile`, which writes outside cwd into `~/.claude/...`, `~/.codex/...`, etc. (acceptable but not contained to a single root).
- Recommendation: documentation note in README that postinstall writes into `~/.claude`, `~/.codex`, `~/.gemini`, `~/.continue`, `~/.aider*`. Already gated by `VEGASTACK_SKIP_SKILL_INSTALL=1`.

### F-006 — Sensitive files (config.json, update-check cache) are not chmod 0600 [Medium]
- Files: `src/lib/update-check.ts:40` (writes to `~/.config/vegastack/update-check.json`), all writes under `~/.vegastack/` from `paths.ts`.
- `chmodSync` is only used to set 0o755 on **executable binaries** (`src/lib/managed-tool-installer.ts:69` etc.). No file is chmod'd to 0o600. If the global config later stores any tokens (e.g., Cloudflare auth, registry tokens), they'd inherit the umask default (often 0644). Today there are no secrets stored — but the pattern is fragile.
- Recommendation: introduce `writeSecretFile(path, body)` helper that applies 0o600 + parent dir 0o700, and use it for any future credential write. Document in `SECURITY.md`.

### F-007 — File writes are not confined to a single safe root [Medium]
- File: `src/lib/paths.ts`
- Writes happen under `~/.vegastack/`, `~/.config/vegastack/` (update-check), `~/.claude/...`, `~/.codex/...`, `~/.gemini/...`, `~/.continue/...`, `~/.aider*`, plus project-cwd files (`AGENTS.md`, `CONVENTIONS.vegastack.md`, `CONTEXT.md`, `gemini-extension.json`, `.cursor/rules/...`). These destinations are **constants**, not derived from user input — so the *risk* is low, but the surface is wide. Symlinks at install time use `linkOrCopyDir` (`src/lib/fs-utils.ts`) which does not check that `dest` resolves inside the expected agent dir.
- Recommendation: in `linkOrCopyDir` and `copyFileWithBackup`, after `fs.lstatSync`, resolve real path and assert `startsWith` of an expected root. Cheap defensive belt.

### F-008 — `assertSafeRelativePath` only used in registry, not in archive extractors [Medium]
- File: `src/lib/registry.ts:539`
- Good helper. Should be lifted to a shared module and reused by all four other installers (see F-002).

### F-010 — sigstore verification can be disabled via env var [Low]

- Recommendation: when this env is set, log a stderr warning unconditionally so it can't be silently active in production.

## Findings

### H-1 — Bare `npm` / `vegastack` spawn fails on Windows (no shell, no `.cmd` resolution)
**File:** `src/commands/update.ts:168`, `src/commands/update.ts:208`
```ts
const r = spawnSync("npm", args, { stdio: "inherit" });
...
const r = spawnSync("vegastack", args, { stdio: "inherit" });
```
On Windows, `npm` and `vegastack` are installed as `npm.cmd` / `vegastack.cmd` shims. `child_process.spawn` without `shell: true` and without `.cmd` resolution will throw `ENOENT` because Windows only resolves `.exe`/`.com` directly; `.cmd`/`.bat` require the shell. This breaks `vegastack update` end-to-end on Windows.
**Fix:** pass `shell: true` (carefully, because args are user-controlled here they aren't) or resolve via `where`/`npm-which`, or special-case `process.platform === "win32"` to suffix `.cmd`.

### H-2 — `tar` / `unzip` assumed available on PATH (Linux/Alpine + bare Windows)
**File:** `src/lib/cloudflared.ts:157`, `src/lib/managed-tool-installer.ts:179, 194`
```ts
spawnSync("tar", ["-xzf", archivePath, "-C", targetDir], ...)
execFileSync("unzip", ["-q", archivePath, "-d", targetDir], ...)
```
- `tar` is reliably present on macOS/Linux, but **Alpine `apk` minimal images** ship with `busybox tar` (works for `-xzf`, OK), and Windows 10+ does have `tar.exe` (also OK), but error path is silent — if missing the user gets `ArtifactCorrupt` with little explanation.
- `unzip` is **not present by default on macOS Sequoia, Alpine, or many minimal Linux images**. The only zip codepath is gated on `win32` (which uses PowerShell — good), but the fallthrough `unzip` for non-Windows zip archives will fail on Alpine.
- The Windows branch shells out to `powershell.exe` `Expand-Archive` — this fails on Windows containers using PowerShell 7 only (`pwsh.exe`) or Server Core variants without Windows PowerShell.

**Fix:** prefer a JS-only extractor (`tar` npm package, `yauzl`/`adm-zip`) so there is no PATH dependency; or detect availability with a clear error.

### H-3 — `apps/dashboard/src/lib/r2.ts` may use Node APIs in a Workers context
**Static check:** Not directly inspected in this pass, but `apps/mcp/src/index.ts` is clean (only Web `Request`/`Response`/`URL`/`fetch`, `console`, `JSON`, `Date`, no `node:fs|child_process|path|os`). However, the `apps/dashboard` is also a Workers app (per `astro.config.mjs` + `wrangler.toml`) and its `r2.ts` is in the modified set — ensure no `node:` imports leak into the Worker bundle.
**Action:** verify with `rg -n "from \\\"node:" apps/dashboard/src` and the Workers build pipeline (nodejs_compat flag posture).

### M-1 — Hardcoded `0o755` chmod and POSIX `chmod` skipped on Windows (correct), but extracted nested binaries not chmodded on POSIX
**File:** `src/lib/managed-tool-installer.ts:67-69`, `src/lib/cloudflared.ts:61-65`
The destination `binPath` is chmodded after `copyFileSync`. That is correct. But if the archive places the binary at a deep path and `findExtractedBinary` walks Windows-style nested zip directory names with mixed case, the `entry.name === binName` compare is **case-sensitive** — it would miss `Cloudflared.exe` on a Windows zip whose top-level dir varies. Likely not currently triggered (assets are lowercase), but fragile. Use `.toLowerCase()` compare.

### M-2 — `spawn`/`spawnSync` for `git`, `rg`, `tar`, `cloudflared` without `process.platform` `.exe` suffix
**Files:** `src/commands/scan.ts` (git), `src/lib/registry-search.ts` (rg via `args.bin`), `src/commands/preview.ts` (cloudflared `bin` resolved via `resolveCloudflaredBin`).
`git`, `rg` invocations work on Windows because the resolved `bin` from `findOnPath` includes the `.exe` (good). However `spawnSync("git", …)` (multiple call sites in `src/commands/scan.ts:382, 688, 1042`) is bare. On Windows `git.exe` is in PATH so it works, but if it ever resolves to `git.cmd` (Git for Windows aliases) it will fail without `shell:true`. Acceptable risk; flag for monitoring.

### M-3 — `~/.vegastack/...` paths can exceed Windows MAX_PATH
**File:** `src/lib/paths.ts`
Path nesting like `~/.vegastack/registry/<entry>/docs/<provider>/<resource>/...` plus generated MANIFEST/sub-trees can exceed 260 chars on Windows when home dir is `C:\Users\<long-name>\AppData\Local\...` style. Long-path support requires `\\?\` prefix or registry opt-in. We do nothing here.
**Mitigations:** keep entry names short; document `git config core.longpaths true`; or detect Windows + warn. No code fix proposed yet.

### M-4 — `process.argv[1]` package root resolution fragile under Windows symlinks
**File:** `src/lib/paths.ts:148-169`
`fs.realpathSync(rawCliPath)` may not resolve npm shim `.cmd` files on Windows (the shim is the actual file; `dist/cli.js` is launched by it via `node`). The walking loop falls back to `path.resolve(path.dirname(cliPath), "..")` which is brittle. Consider using `import.meta.url` + `fileURLToPath` consistently (already used in `npm/run.js`).

### L-2 — Newline splits already CRLF-safe except 3 sites

### F-001 — `vegastack preview` shells user-supplied command via `bash -c` (command injection)
- **Severity:** high
- **Location:** `src/commands/preview.ts:85-90` (`spawnShell`) and `src/commands/preview.ts:186-192`
- **Evidence:**
  ```ts
  function spawnShell(command: string): PreviewChild {
    return spawn(command, {
      shell: true,
      stdio: ["ignore", "pipe", "pipe"],
      env: { ...process.env, BROWSER: "none" },
    });
  }
  ```
  `--command "$(rm -rf ~)"` or any compound command flows straight into the shell. The same `command` is also auto-derived from `package.json#scripts.dev`/`start` (also string-interpolated with the package manager name), so a hostile `package.json` triggers shell execution on the operator's machine just by running `vegastack preview` in that repo.
- **Suggested fix:** Tokenize via `shell-quote` or accept `--command` as a string but document it; for `detectDevCommand` use `spawn(pm, ["run", scriptName])` (array form) instead of `${pm} run dev` interpolated into a shell. Drop `shell: true` for the auto-detected branch.
- **Suggested test:** Add `tests/commands/preview-injection.test.ts` that supplies a `package.json` with `scripts.dev = "; touch /tmp/pwned"` and asserts the touch did not happen.

### F-002 — `vegastack update` shells out to `npm i -g` and a recursive `vegastack` re-spawn without `PATH` validation
- **Severity:** high
- **Location:** `src/commands/update.ts:166-178` and `src/commands/update.ts:202-216`
- **Evidence:**
  ```ts
  const r = spawnSync("npm", args, { stdio: "inherit" });
  ...
  const r = spawnSync("vegastack", args, { stdio: "inherit" });
  ```
  `npm` and `vegastack` are resolved through the user's `PATH`. On Windows, `spawnSync("npm", …)` without `shell: true` will fail (npm is `npm.cmd`). On Unix, a hostile `~/.local/bin/npm` shadow earlier in PATH would be invoked with `-g`. There is no integrity check, no fallback to `process.execPath`-based resolution, and no `--cli=false` short-circuit if no global write permission exists.
- **Suggested fix:** Use `process.execPath` + the npm script path (npm exposes `npm_execpath`); on Windows append `.cmd`. For the recursive call, prefer re-invoking the current entrypoint via `process.argv[0] process.argv[1] update --no-cli --no-registry`. Detect EACCES on global install and emit actionable next-step (sudo/`--prefix`).
- **Suggested test:** `tests/commands/update.test.ts` mocking `spawnSync` to assert Windows uses `npm.cmd` and self-respawn uses `process.argv[1]`.

### F-003 — Pre-commit hook writer does not respect `core.hooksPath` for `init` path / project-init writer
- **Severity:** high
- **Location:** `src/commands/scan.ts:251-285` and `src/commands/init.ts:345`

### F-004 — `vegastack scan --output <path>` writes anywhere with no containment check
- **Severity:** high
- **Location:** `src/commands/scan.ts:117`
- **Evidence:**

### F-006 — `runPreview` doesn't `await child.kill` on SIGINT and may leak grandchildren when `shell: true`
- **Severity:** medium
- **Location:** `src/commands/preview.ts:268-279`
- **Evidence:** Because the dev server is started with `shell: true`, `child.kill("SIGTERM")` only kills the shell — Node + dev server (e.g., next.js) often survive as orphans. ### F-D01 [high] aliases.yaml is re-read & re-parsed on every discover() call (no cache)

**File:** `src/lib/discover/aliases.ts:38-71`

`loadAliases()` does `fs.readFileSync` + `yaml.load` every invocation with **no
caching whatsoever**. It is called multiple times per `discover()` request:

2. Once per `knownProvider` inside `detectMultiProviderPhrasing` (line 842-849

3. Once per `knownProvider` inside `detectProviderFromAliasFiles` (line 1003-1014
   in `index.ts`) — **N more file reads + N more YAML parses** when classifier
   produced no provider.

For ~30 providers this is 30–60 sync FS calls + YAML parses per query, on the
hottest path of the CLI. `manifest.ts` already implements an mtime-keyed
`CACHE` for the same access pattern; adopt the identical pattern in
`aliases.ts`.

**Fix:** add an `mtimeMs`-keyed cache around `loadAliases` (mirror
`loadManifest` in `manifest.ts`). Expose `clearAliasesCache()` for tests.

### F-D02 [high] knowledge/ and recipes/ directories rescanned + every file re-read on every call

**Files:** `src/lib/discover/knowledge.ts:42-95`, `src/lib/discover/recipes.ts:33-89`

Both loaders walk the entire `knowledge/` (markdown) and `recipes/` (TOML)
directories on every `discover()` call: `readdirSync` + `readFileSync` +
`gray-matter` / `TOML.parse` per file.

`knowledge.ts:54` and `recipes.ts:45` perform a sync read for **every** card,
then YAML/TOML parse, then trigger-match. There is no caching layer — the
directories are walked even for queries that don't match any card.

For a Registry pack with ~50 knowledge cards + ~30 recipes, each query incurs
~80 sync reads + 80 frontmatter parses. This dominates `tokenize_ms` and
`enrich_ms` once the pack grows. A single mtime-keyed cache (per-file or
per-directory) would amortize this to zero on warm calls.

**Fix:** mtime-keyed cache (key = filepath, value = `{mtimeMs, parsed}`); only
re-parse when stat differs.

### F-D03 [high] `tier1`/`tier2` "parallel" Promise.all is fake — both run sync on the event loop, with subprocess spawns blocking it

**File:** `src/lib/discover/index.ts:444-455`

```ts
const [t1, t2Result] = await Promise.all([
  Promise.resolve(tier1({...})),
  Promise.resolve(tier2({...})),
]);
```

Both `tier1` and `tier2` are **synchronous** functions. `Promise.resolve(syncCall())`
evaluates the sync call BEFORE constructing the promise — so the two run
**strictly sequentially**. The `tokenize_ms` and `tier1_ms` timings just before
this confirm it (both clocks start before the await).

Worse: `tier2` calls `spawnSync('rg' | 'grep' | 'find')` up to 5+ times
sequentially per query (one per token in pass A, plus pass B/C/D). Each
`spawnSync` blocks the entire Node event loop for the subprocess duration
(timeout 10 s). The misleading "parallel" comment in the pipeline header
(`index.ts:14`) implies a perf characteristic that doesn't exist.

**Fix options:**
1. Switch tier2's grep functions to `spawn` + Promise; then `Promise.all` is real.
2. Or document that tier2 is sync and remove the misleading comment.
3. Or move tier2 grep passes into a worker thread.

This is also a latency cliff for `vegastack ask` on cold caches when tier1
quality gate fails.

### F-D04 [high] `mergeOkEnvelopes` knowledge/recipes dedup by id silently overwrites

**File:** `src/lib/discover/index.ts:657-663`

```ts
for (const env of envelopes) for (const k of env.knowledge) knowledgeById.set(k.id, k);
```

Last-write-wins. If two providers in an auto-merged ambiguous envelope return
the same knowledge id (a card with `providers: [aws, gcp]` matched in both
sub-envelopes), the second envelope's instance silently overwrites the first.
Today the cards are identical (loaded from the same file), so the bug is
latent — but the merge envelope ordering depends on `Promise.all` resolution
order which is **deterministic only because** the inputs are array-ordered;
any future change to envelope ordering (e.g. resolving fastest-first) would
silently change results.

**Fix:** if the cards are guaranteed-identical, use `set` only when key is
absent (`if (!knowledgeById.has(k.id)) knowledgeById.set(k.id, k)`); or merge
provider lists. Same fix for `recipesById`.

**File:** `src/lib/discover/tier2.ts:163-169`

### F-SCAN-001 [CRITICAL] `runScan` references undefined identifier `ok` — command always returns success/failure based on a ReferenceError surface
File: src/commands/scan.ts:110


`ok` is not defined anywhere in `runScan`. The intended source is `payload.ok`. At runtime this will throw `ReferenceError: ok is not defined`, which is then caught by the surrounding `try/catch` and routed to `printError(e)`. Net effect: **every** invocation of `vegastack scan` returns a non-zero error exit (or whatever `printError` returns) and the JSON/text report is still printed (lines 107-109 run before the error), but the success path is unreachable. This is a P0 functional bug in the security scanner's primary entrypoint and almost certainly breaks pre-commit hook usage (`vegastack scan --staged` will always "fail").

Fix: `return payload.ok ? 0 : 1;`. Add a regression test that asserts exit code 0 on a clean repo.

### F-SCAN-002 [HIGH] Subprocess `env` defaulting drops PATH when caller passes a partial env
File: src/lib/scan-tools.ts:66-83 (`runTool`)

`spawnSync` is invoked with `env: opts.env`. When `opts.env` is `undefined` Node defaults to `process.env` (fine), but several call sites pass a constructed env object that *omits* PATH, e.g. command `scanActions` zizmor invocation (src/commands/scan.ts:462-465) only adds `ZIZMOR_OFFLINE` and spreads `process.env` (OK there), but the pattern is fragile: if any future caller forgets `...process.env`, the scanner subprocess loses PATH and on macOS/Linux many tools (e.g. trivy invoking git) silently break. Recommend `runTool` to always merge `{ ...process.env, ...opts.env }` rather than passing the caller's env raw.

Also, `runTool` does not set `shell: false` explicitly. Default for `spawnSync` is `false`, so command/argv are not shell-interpreted (good), but this should be asserted with a comment to prevent regression.

### F-SCAN-003 [HIGH] `installScanPreCommitHook` corrupts existing hooks under common conditions
File: src/commands/scan.ts:241-275

Logic flow:
1. If hook file exists with `# vegastack scan:start` marker, the block is replaced via regex. OK.
2. Else if file is anything other than literally `#!/bin/sh` and `force` is false, refuse. OK.
3. Else **append** the block.

Branch (3) triggers when (a) the file does not exist (caught by try/catch -> `raw = "#!/bin/sh\n"`), or (b) `force` is true. In the `force=true` path on a non-empty user-authored hook, the existing hook body is **kept** but our block is appended. That part is fine. However:
- If the file does not exist, we set `raw = "#!/bin/sh\n"`. The trailing `\n` is preserved by `trimEnd()` then `\n\n${block}` is appended → final hook starts with `#!/bin/sh\n\n# vegastack scan:start\n...` which is correct.
- But the catch is unconditional (`catch { raw = "#!/bin/sh\n"; }`) — this catches **EACCES, EISDIR, EBUSY**, not just ENOENT. If the user has a non-readable existing hook, we silently overwrite their content. Should narrow to `code === "ENOENT"`.

Also: hook is written with `mode: 0o755` then immediately `chmodSync(hookPath, 0o755)` on non-Windows — redundant. `fs.writeFileSync` with `mode` only applies on file *creation*, not when overwriting. Existing-file permissions are preserved unless `chmodSync` runs — so on Windows the chmod is skipped and a previously non-executable hook stays non-executable. Minor.

### F-SCAN-005 [HIGH] `--output` writes to an arbitrary user-supplied path with no validation
File: src/commands/scan.ts:107


The path is not resolved relative to project root and not validated to live within cwd. ### F-SCAN-007 [MEDIUM] Tool resolution falls back to PATH first match without integrity check

### F-SCAN-008 [MEDIUM] Subprocess `maxBuffer: 100MB` and JSON.parse of full stdout — DoS / memory exhaustion vector

### F-REG-001 — [CRITICAL] Managed-tool downloads have no signature/provenance verification, only a manifest-pinned SHA256

File: src/lib/managed-tool-installer.ts:147-170, src/lib/cloudflared.ts:136-154

Managed tools (cloudflared, ripgrep, gitleaks, actionlint, osv-scanner, trivy, zizmor) are downloaded straight from `https://github.com/<repo>/releases/download/<ver>/<asset>` and verified ONLY against `target.sha256` baked into `src/lib/managed-tools-manifest.ts`. The manifest itself ships inside the npm tarball, so the trust root is "whatever was committed to this repo when the npm version was published". There is no:

- Sigstore / cosign verification of the GitHub release asset (unlike registry catalog, which DOES verify via sigstore — see registry-signature.ts).
- Cross-check against upstream's published checksums file.
- Detached signature check.

Blast radius: a compromised npm package containing a tampered `managed-tools-manifest.ts` (matching a malicious asset) will silently install a backdoored binary onto the user's `~/.vegastack` and run it (e.g. ripgrep is invoked synchronously by `vegastack search`). Compare with registry.ts which calls `verifyRegistryCatalogSignature()` before parsing the catalog — that defense is missing for managed tools.

Fix: verify each release asset against an upstream-published signature (cosign for trivy/osv-scanner/zizmor, minisign/checksums for others) before copying into `destDir`, OR pin the GitHub release by an immutable tag-with-digest assertion via the GitHub API and verify the actions/attestations bundle (https://docs.github.com/en/actions/security-guides/using-artifact-attestations-to-establish-provenance-for-builds).

### F-REG-002 — [HIGH] Zero network timeouts on every download (registry catalog, archives, managed tools)

Files: src/lib/registry.ts:410, 425; src/lib/managed-tool-installer.ts:152-160; src/lib/cloudflared.ts:136-145

Every `fetch(url, { redirect: "follow" })` call lacks `signal` / `AbortController` and does not enforce a body-size cap. A slow-loris or hung server stalls the CLI indefinitely. There is also no retry policy.

Fix: wrap each fetch with `AbortSignal.timeout(60_000)` (or env-tunable), reject responses with no `Content-Length` above a sane cap, and add a small retry-with-backoff for 5xx/network errors.

### F-REG-003 — [HIGH] Archive extraction shells out to host `tar` / `unzip` / `powershell.exe`, with no defense against symlinks or device files inside the archive

File: src/lib/registry.ts:447-466 (`extractVerifiedArchive`); src/lib/managed-tool-installer.ts:172-198 (`extractArchive`); src/lib/cloudflared.ts:156-170 (`extractTar`).

`registry.ts` does pre-list the archive with `tar -tzf` and runs `assertSafeRelativePath()` on each entry, which blocks the basic zip-slip via `..` or absolute paths. **However:**

1. `tar -tzf` lists *names*, not types — a symlink whose name is benign (e.g. `docs/cheatsheet.md`) but whose link target is `/etc/passwd` or `../../.ssh/authorized_keys` passes the check, then `tar -xzf` follows it on extraction. GNU tar is hardened against this since 1.32, but BSD tar (default on macOS / Alpine `bsdtar`) is not. Same applies to hardlinks and device/FIFO entries.
2. `managed-tool-installer.ts` and `cloudflared.ts` skip the listing pre-check entirely and call `tar -xzf` directly. There is no entry-type filter and no `--no-same-owner --no-same-permissions`.
3. On Windows, `Expand-Archive` similarly does not block junctions/symlinks; `unzip` on Linux honors symlinks.

Fix: switch to a Node-side extractor (e.g. `tar` npm package with `filter` + `onentry` + `strict: true` rejecting non-file/dir types) or pass `--no-same-owner --no-overwrite-dir` plus an explicit `--exclude '*' --include` whitelist; reject entries where `entry.type !== 'File' && entry.type !== 'Directory'`.

### F-REG-004 — [HIGH] `tests/fixtures/safe-tar/traversal.tar.gz` is not exercised by any test in this slice

`grep -r traversal.tar.gz src/ tests/` returns nothing. The fixture exists but nothing imports/reads it, so the zip-slip / symlink defenses above are not regression-tested. Combined with F-REG-003, the only protection is human code review.

### F-REG-005 — [HIGH] `urlFor()` strips and trims the path but the catalog `entry.archive` field is never validated against the registry base host

File: src/lib/registry.ts:378-388

```

  const cleaned = relativePath.replace(/^\/+/, "").replace(/^registry\//, "").replace(/^cli\//, "");
  return `${registryBaseUrl()}/${cleaned.split("/").map(encodeURIComponent).join("/")}`;

```

`relativePath` comes from `entry.archive` which is signed via the catalog signature, so an attacker who lacks the sigstore key can't forge it. **However**, `VEGASTACK_REGISTRY_URL` is read from env with no allowlist — any user (or a malicious shell-rc / direnv) can repoint the CLI to any HTTP host, and because `entry.archive` is just appended, an attacker controlling that host controls all downloads. ### F-REG-006 — [HIGH] No proper-lockfile / mutex around install — concurrent `vegastack registry update` races corrupt the cache

Files: src/lib/registry.ts:262-292; src/lib/managed-tool-installer.ts:54-73; src/lib/cloudflared.ts:51-69.

### F-REG-007 — [HIGH] `installPublishedRegistryEntry` rollback path is racy and can lose user state

File: src/lib/registry.ts:277-287

```

if (fs.existsSync(dest)) fs.renameSync(dest, aside);
try {
  fs.renameSync(nextRoot, dest);
} catch (e) {
  if (fs.existsSync(aside) && !fs.existsSync(dest)) fs.renameSync(aside, dest);
  throw e;
}

```

If the process is killed (SIGKILL / power loss) between `rename(dest, aside)` and the next `rename(nextRoot, dest)`, the cache is left in an `aside` directory the CLI doesn't know about, and `dest` is gone. Fix: use a single atomic rename of a sibling staging dir into place (POSIX `rename` is atomic for directories on the same fs), and on startup garbage-collect any `${dest}.old-*` orphans.

### F-REG-010 — [MEDIUM] `extractVerifiedArchive` `tar -tzf` listing is parsed by line-split — entries containing newlines bypass the path check

A tar entry whose filename contains `\n` (legal in POSIX) is split into two "lines"; the second line could be a benign-looking suffix while the actual entry name `../../etc/passwd\nfoo` slips through (the first line `../../etc/passwd` *would* be rejected, but tar's `-tzf` output prints just the name on one line — however with newlines in the filename, the listing is ambiguous and `-tzf` does not escape). ## CRITICAL

### S-C1 — `update-managed-tools-manifest.ts`: trust-on-first-use for GitHub release digests, no signature/provenance verification
File: `/Users/mk/projects/vegastack-cli/scripts/update-managed-tools-manifest.ts:188-243`

`buildTool` derives sha256 values from one of three sources, all of which trust a single TLS fetch from `api.github.com`/`github.com`:
1. `ghAsset.digest` — a field GitHub computes server-side from the uploaded artifact. If the upstream repo's release pipeline (or GitHub itself) is compromised, this value is attacker-controlled.
2. `checksumText` — fetched over HTTPS from the same release's assets list (`fetchAssetText`). Same trust boundary as the binary itself: an attacker who can replace the binary in a release also replaces `*_checksums.txt`.
3. `parseChecksum` from a per-asset `.sha256` sidecar — same trust boundary.

There is no:
- Signature verification (no cosign / minisign / sigstore / GPG check, even when upstream publishes them — e.g., `cloudflared`, `trivy`, and `gitleaks` all publish cosign signatures).
- Cross-source check (e.g., GitHub `digest` API vs the upstream-provided `*_checksums.txt`).
- Pinning of the GitHub API to an exact commit/tag we previously verified — the script always asks `releases/latest`, so a forced retag of an old version with new artifacts is silently accepted.

Because the resulting manifest is committed to `src/lib/managed-tools-manifest.ts` and consumed by `installManagedTools` to verify downloads, a single bad run of this script (e.g., upstream tag move + GitHub API momentary inconsistency, or a compromised upstream release) bakes an attacker-controlled sha256 into the published npm package. End-user installs then "verify" the malicious binary against the malicious checksum and run it.

Recommendations (any one of these closes the gap; ideally all three):
- Cross-verify the `digest` field against the published `*_checksums.txt` and fail if they disagree.
- For tools that publish cosign/minisign signatures (cloudflared, trivy, gitleaks, ripgrep), shell out to `cosign verify-blob` / `minisign -V` against a pinned public key committed in the repo.
- Make manifest updates require human review of a *two-source* diff: store `digest_source: "gh-api" | "checksum-file" | "both"` per target and refuse to publish if any target dropped to a single source.

## HIGH

### S-H1 — `update-managed-tools-manifest.ts`: unauthenticated GitHub API calls, no rate-limit handling, no `tag_name` allowlist
File: `/Users/mk/projects/vegastack-cli/scripts/update-managed-tools-manifest.ts:267-273, 188-194`

`fetchText` does not pass `Authorization: Bearer $GH_TOKEN` even when running in CI (`.github/workflows/managed-tools-weekly.yml` is in scope per the git status). Consequences:

- Anonymous GH API quota is 60 req/hour/IP. A retry of the workflow on a shared GH-hosted runner can blow the quota and cause partial-success runs (HIGH H2 below).
- The script does not whitelist acceptable `tag_name` shapes. If upstream cuts a malformed/draft tag (e.g., `nightly-2026-05-06`), the `version` flows verbatim into asset templates and into the committed manifest. Combined with the lack of a "downgrade detection" check, a downgrade or a bogus tag is silently accepted.
- No timeout on `fetch` — a hung GitHub edge node hangs CI indefinitely.

Recommendations: pass `GH_TOKEN` if present; require `tag_name` to be `vX.Y.Z` (or pass an explicit `versionForAsset` regex check); refuse to write the manifest if the new version sorts lower than the existing manifest's version; add `AbortSignal.timeout(30_000)`.

### S-H2 — `update-managed-tools-manifest.ts`: not idempotent on partial failure — leaves manifest in mixed-version state
File: `/Users/mk/projects/vegastack-cli/scripts/update-managed-tools-manifest.ts:171-186`

`main()` builds the `tools` map sequentially via `for (...) tools[spec.name] = await buildTool(spec)` and only writes `OUT` after **all** tools succeed. Good. **But**: `buildTool` itself fans out per-target `Promise.all` (line 208-221) and calls `fetchAssetText` once per target on the slow path. A flaky network mid-tool throws and the *entire* run aborts. There is no resume / cache; the next CI re-run re-fetches everything from scratch. Worse, `generated_at` is computed as the max of each tool's `published_at`, so a re-run that lands on a new upstream release for one tool but reuses the prior manifest result for another tool (e.g., a developer manually edits) silently desyncs the top-level `generated_at` from the per-tool `generated_at`.

Recommendation: cache successful per-tool results in a `.tmp/` dir keyed by `(repo, tag_name)` and resume; emit a summary table with explicit `unchanged/updated/failed` per tool; fail the whole run on any failure rather than partial writes.

### S-H3 — `smoke-managed-tools.ts`: smoke test pollutes `process.env` for the parent process, no cleanup of `VEGASTACK_CONFIG_DIR`
File: `/Users/mk/projects/vegastack-cli/scripts/smoke-managed-tools.ts:11-13, 86-88`

`process.env.VEGASTACK_CONFIG_DIR = path.join(tmp, "config")` is set on the running Node process and *never* cleared. The `finally` block deletes the temp dir but the env var still points there. If this module is imported into a longer-running process (e.g., the eval runner, or a future composite script), subsequent calls into `installManagedTools()` will silently target the deleted path. Today this is fine because the script exits, but as a CI building block it's a footgun. Also, `installManagedTools({ force: true })` will redownload all tools on every CI run (no cache) — slow and burns GitHub release-asset bandwidth.

Recommendation: snapshot/restore env, or use `withConfigDir(tmp, fn)` helper. Optionally accept a `--cache` flag to reuse a workflow cache between runs.

### S-M3 — `update-managed-tools-manifest.ts`: `parseChecksum` is substring-anchored — false-positive risk
File: `/Users/mk/projects/vegastack-cli/scripts/update-managed-tools-manifest.ts:245-252`

`if (!line.includes(asset)) continue;` matches any line containing the asset name as a substring. If a checksum file contains `cloudflared-darwin-amd64.tgz` and `cloudflared-darwin-amd64.tgz.sig` in that order, the lookup for `cloudflared-darwin-amd64.tgz` returns the first match by accident — but if the order ever flips upstream, you'd silently use the `.sig` file's hash as the binary's expected hash. ### S-M4 — `generate-skills.ts`: `JSON.stringify(r.providers)` and `JSON.stringify(p.providers)` interpolated into YAML frontmatter

### S-M5 — `generate-skills.ts`: `ensureCleanDir` deletes user-edited files without warning

## Findings

### F-NPM-01 — `postinstall` swallows ALL errors with `|| true` [High]
**File:** `package.json:78`
```
"postinstall": "node npm/install.js || true",
```
The `|| true` masks every failure mode: syntax errors in `install.js`, Node version mismatches (the script uses ESM + top-level `import.meta.url`, requires Node >= 14.13), missing `node` on PATH, OOM, EACCES, etc. Although the script *itself* is carefully written to be non-fatal (it logs and continues on every branch), the shell-level `|| true` defeats observability: a user running `npm install` with `--foreground-scripts` will never see a non-zero exit, and `npm` will never propagate it to their CI logs.

The script is already best-effort internally — wrapping it in `|| true` adds nothing except hiding bugs introduced in `install.js` itself (e.g., a future syntax error would silently skip postinstall on every user's machine for an entire release cycle).

**Recommendation:** Remove `|| true`. Let `install.js` own its own non-fatal semantics (it already does, via try/catch-equivalent branching and writing only to stderr). If you want belt-and-suspenders, wrap the *body* of `install.js` in a top-level try/catch that always exits 0, but do not silence at the shell level.

---

### F-NPM-02 — Bin shim is not guaranteed LF / 0755 at publish time [High]
**Files:** `npm/run.js`, `npm/install.js`, `package.json` (no `prepack`/publish guard)

`npm/run.js` starts with `#!/usr/bin/env node` (correct), but:
1. There is no `.gitattributes` or publish-time check forcing LF line endings on `npm/*.js`. If a Windows contributor commits with CRLF (`core.autocrlf=true`), the published tarball will contain `#!/usr/bin/env node\r`, which on Linux/macOS produces the classic `env: node\r: No such file or directory` error.
2. There is no explicit chmod / file-mode check. npm *does* set the executable bit on `bin` entries during install on POSIX, so this is usually fine — but if the file is committed without 0644 on a filesystem that loses mode (some Windows checkouts), and a future change moves to a directly-invoked path, this will regress.

**Recommendation:** Add `.gitattributes` with `npm/*.js text eol=lf` (and `* text=auto`). Optionally add a `prepack` assertion that reads `npm/run.js` and aborts if it contains `\r`.

---

### F-NPM-03 — `postinstall` does not honor `npm_config_ignore_scripts` directly, and ignores `INIT_CWD` semantics [High → reclassify Medium on closer read]

Re-read: npm itself respects `--ignore-scripts` / `npm_config_ignore_scripts=true` by *not running the postinstall at all*, so this is handled upstream. `INIT_CWD` is only relevant if the script writes to the user's project — `install.js` does not write anywhere on disk (only spawns the CLI's `skills reconcile --scope global`, which writes to `~/.claude/skills/...` in the user's home, not to `INIT_CWD`).

However: the `skills reconcile --scope global` subprocess *does* write to the user's home directory during `npm install`. This is surprising behavior for a postinstall — many users (including corporate CI) consider any writes outside `node_modules` during `npm install` to be a smell. There is an env opt-out (`VEGASTACK_SKIP_SKILL_INSTALL=1`) which is good, but it is opt-out, not opt-in.

**Recommendation:** Document this in README + CHANGELOG ("postinstall registers a global agent skill in `~/.claude/skills/vegastack` unless `VEGASTACK_SKIP_SKILL_INSTALL=1`"). Consider flipping to opt-in for v1.0. At minimum, ensure CI environments (`process.env.CI`) skip the global write by default — corporate CI runners often share `$HOME` across jobs and will accumulate stale skills.

**Severity:** High (surprising filesystem write during `npm install` outside `node_modules`, opt-out only, no `CI` detection).

### F-NPM-04 — `VEGASTACK_POSTINSTALL_TIMEOUT_MS` parse accepts negative / NaN silently [Medium]
**File:** `npm/install.js:34-37, 45`
```js
const timeoutMs = Number.parseInt(process.env.VEGASTACK_POSTINSTALL_TIMEOUT_MS ?? "15000", 10);
...
timeout: Number.isFinite(timeoutMs) && timeoutMs > 0 ? timeoutMs : 15000,
```
The fallback handles NaN and negatives, which is good. Minor: `parseInt("15000abc")` returns `15000` silently — set `VEGASTACK_POSTINSTALL_TIMEOUT_MS=15000abc` and the user thinks they're getting custom behavior. Low impact, but worth a stricter regex check or `Number()` (which returns NaN for `"15000abc"`).

**Recommendation:** Use `Number(process.env.VEGASTACK_POSTINSTALL_TIMEOUT_MS)` and validate.

### F-NPM-05 — `process.env` is forwarded wholesale to the spawned CLI [Medium]
**File:** `npm/install.js:40-43`
```js
env: { ...process.env, VEGASTACK_POSTINSTALL: "1" },
```
The full parent environment is forwarded to `dist/cli.js`. During `npm install`, this env contains many `npm_*` variables, `INIT_CWD`, `npm_config_*` (which can include private registry tokens like `npm_config_//registry.npmjs.org/:_authToken=...`). Forwarding to a child Node process is normal and not itself a leak — but if the child CLI ever logs `process.env` (e.g., via a verbose/debug flag, a crash report, telemetry), the token can escape.

**Recommendation:** Strip `npm_config_*` and `npm_token`-ish keys before forwarding. Defense in depth.

### F-NPM-06 — `spawnSync` stdout is `"ignore"`, swallowing useful diagnostics [Medium]
**File:** `npm/install.js:39`

### F-NPM-07 — No Node-version preflight in `install.js` or `run.js` [Medium]
