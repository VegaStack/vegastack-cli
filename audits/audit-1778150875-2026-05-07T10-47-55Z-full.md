### F-001 — `vegastack update` cannot upgrade itself on Windows (npm.cmd shim)
- **Severity:** high
- **Category:** cross-platform
- **Location:** `src/commands/update.ts:168`
- **Cited line:** `  const r = spawnSync("npm", args, { stdio: "inherit" });`
- **Evidence:**
  ```ts
  // src/commands/update.ts 166-178
  const args = ["i", "-g", `${PKG_NAME}@latest`];
  log.step(`running: npm ${args.join(" ")}`);
  const r = spawnSync("npm", args, { stdio: "inherit" });
  if (r.error !== undefined) {
    throw r.error;
  }
  if ((r.status ?? 0) !== 0) {
    throw new Error(`npm exited ${r.status ?? "?"}; see output above`);
  }
  ```
  On Windows, `npm` is distributed as `npm.cmd` (a batch shim). Node's
  `child_process.spawn`/`spawnSync` without `shell: true` cannot exec
  `.cmd`/`.bat` files directly — the call returns `ENOENT`. Since Node
  v18.20.2 / v20.12.2, even when it does run, executing `.bat`/`.cmd`
  without shell is blocked entirely (CVE-2024-27980). Result: every
  Windows user invoking `vegastack update` hits a hard failure.
- **Suggested fix:** Use `spawnSync(npmCmd, args, { stdio: "inherit", shell: false })`
  where `npmCmd` is `"npm.cmd"` on win32 and `"npm"` elsewhere; or pass
  `shell: true` and properly quote `args`. Same for the
  `spawnSync("vegastack", ...)` call at `update.ts:208` and the
  `spawnSync("npm", ...)` call at `src/lib/update-check.ts:64`.
- **Suggested test:** Add `tests/commands/update-windows.test.ts` that
  mocks `process.platform = "win32"` and asserts the spawned command name
  ends with `.cmd`.

# Code Review — discover slice (`src/lib/discover/*.ts`)

Hot-path focus: O(n²) loops, sync I/O in tight loops, cache-key correctness, memory bounds, deterministic ranking.

Files audited (17):
aliases.ts, bigrams.ts, constants.ts, enrich.ts, index.ts, intents.ts, knowledge.ts, manifest.ts, merge.ts, path-weight.ts, provider.ts, recipes.ts, scoring.ts, tier1.ts, tier2.ts, tokenize.ts, types.ts.

## Summary

The discover pipeline is generally well-structured with explicit timing instrumentation, mtime-keyed caching for `MANIFEST.json`, and deterministic tie-breakers. The biggest hot-path concerns are (1) **`aliases.ts` has no cache** and is invoked O(N_providers) per ambiguous query through three independent paths, (2) **`knowledge.ts` and `recipes.ts` re-read+re-parse every channel file on every call** and run once per provider in fanout mode, and (3) the **`Promise.all` of synchronous CPU work in tier1+tier2 is fake parallelism**. Several Tier-1 stages do redundant `Object.entries` allocations per token.

# Code Review — Registry Slice

Scope: `src/lib/registry.ts`, `src/lib/registry-search.ts`, `src/lib/registry-signature.ts`, `src/lib/managed-tools.ts`, `src/lib/managed-tools-manifest.ts`, `src/lib/managed-tool-installer.ts`, `src/lib/cloudflared.ts`, `src/lib/ripgrep.ts`. Focus: signature verification, archive extraction (zip-slip / symlink), URL allowlist, atomic writes, proper-lockfile, network timeouts, TLS.

## Summary

- Catalog signing via `sigstore` + identity regex is in place and correctly fails-closed (only `VEGASTACK_REGISTRY_VERIFY=0` opt-out), with SHA256 + size verification of the archive and per-file artifact-index verification.
- However, the slice has structural gaps that increase blast radius: (1) the registry base URL is fully overridable by environment with no allowlist or `https:` enforcement, (2) zero `fetch` timeouts so a hung mirror hangs the CLI, (3) downloads are buffered fully into memory with no max-size guard prior to checksum, (4) tar/zip extraction is delegated to system `tar`/`unzip`/`Expand-Archive` without symlink containment — the listing-prefilter in `registry.ts` only inspects path strings, not symlink targets, so a tar that contains a symlink whose name passes `assertSafeRelativePath` can still be extracted by `tar -xzf` and subsequent writes can escape the staging dir, (5) installs lack file-locking so concurrent `vegastack` runs race on the cache rename, (6) artifact final writes use `writeFileSync` instead of temp+rename atomic writes.
- `registry-search.ts` correctly post-verifies match files against `ARTIFACTS.json` SHA but only when an artifact entry exists; files outside the index silently pass through `verified: false` with no policy enforcement.

### F-001 — Validate `VEGASTACK_REGISTRY_URL` against an allowlist and require https
- **Severity:** high
- **Category:** code-review/registry
- **Location:** `src/lib/registry.ts:387`
- **Cited line:** `  return (process.env.VEGASTACK_REGISTRY_URL ?? DEFAULT_REGISTRY_BASE_URL).replace(/\/+$/, "");`
- **Evidence:**
